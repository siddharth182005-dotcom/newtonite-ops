# Engineering decisions

## 1. Relational work items and append-only activity
**Context:** users need clear ownership, state, and an explainable history. **Options:** event sourcing, a JSON audit blob on each item, or normalized tables with a separate event log. **Choice:** normalized entities and append-only `activity_logs` rows written in the same database transaction as each important mutation. The item key is a generated column (`OPS-` plus 1000 and the row id), avoiding a sequence race. **Trade-off:** the activity log explains changes but cannot replay them; its growth and partitioning are deferred.

## 2. Atomic claims, version checks, and idempotency
**Context:** simultaneous claims and edits, plus uncertain network retries, must not silently lose or duplicate work. **Options:** frontend locking, row/advisory locks, conditional updates, or compare-and-swap versions. **Choice:** conditional `UPDATE ... WHERE assignee_id IS NULL` for claims; integer version compare-and-swap with a 409 and current record for edits; and per-user idempotency keys with payload fingerprints and a unique constraint for creates. **Trade-off:** clients must retain versions and reuse keys only for retries of the same request; keys expire after 24 hours. PostgreSQL race and retry tests exercise these guarantees.

## 3. Central team-scoped authorization
**Context:** users can hold different roles across teams, and protected records must not leak across team boundaries. **Options:** ad-hoc route checks, PostgreSQL row-level security, or a shared application permission service. **Choice:** `authz.py` centralizes permission levels and workflow authorization; SQL list queries are scoped to the caller, non-member item access returns 404, and insufficient in-team roles return 403. Authorization is enforced by the API, not only by frontend controls. **Trade-off:** application-level scoping can be omitted in a future query (database RLS would add defense in depth); RLS is deferred.

## 4. Transactional outbox for secondary work
**Context:** assignment notifications should not be lost or duplicated when a worker fails. **Options:** send inline, use an in-process task, introduce a broker, or persist an outbox. **Choice:** the state change, activity event, and outbox job commit together; a polling worker claims jobs with `SKIP LOCKED`, retries with bounded backoff, and uses an idempotent notification handler. **Trade-off:** polling adds latency and an extra process; the current handler creates an in-app notification rather than sending email. Email, WebSockets, attachments, SSO, rate limiting, and administration UI are intentionally out of scope and listed in `KNOWN_LIMITATIONS.md`.

## 5. Server-side search, pagination, and consistent presentation
**Context:** the application should remain useful with tens of thousands of work items while keeping dashboard and list behavior understandable. **Options:** load/filter in the browser, use cursor or offset pagination, and duplicate dashboard-specific endpoints or compose views into the item list. **Choice:** permission-scoped SQL search/filtering with escaped `ILIKE`, stable ordering, bounded offset pagination, and indexes; the needs-attention queue composes with the existing list filters. CSS variables mirrored by typed tokens keep the interface theme consistent and are checked by tests. **Trade-off:** deep offsets and unindexed substring search become slower; the attention rule and UI signal tags still have some duplication. Keyset pagination, a trigram index, and further rule consolidation are documented follow-ups.
